# redis缓存三兄弟：穿透、击穿、雪崩

## 问题一：为啥非要加缓存？不加行不行？

**简单说，缓存就是【把热点数据放内存里，别每次都打数据库】。数据库（尤其MySQL）抗并发能力有限，QPS上不去几千就喘。把频繁读的数据塞进 Redis 这种内存库，读请求直接命中内存，快100倍不止，不加行不行？小项目行，但一旦并发上来，数据库直接被打挂掉，整站崩，所以缓存的本质是【给数据库挡枪】**

## 问题二：缓存穿透：查一个根本不存在的id,为啥能把数据库搞死？

**穿透说的是一请求查的数据【数据库里也没有】。比如有人刷id = -1或者乱填的垃圾key。因为数据库中没有，缓存里自然也没有，每次请求都穿透缓存直接打到数据库。黑客拿一堆不存在的key狂刷，数据库就被这种无效请求压垮。关键点：它不是缓存失效，而是【查的东西压根不存在】，所以每次都落在库中**
**怎么治穿透？布隆过滤器+空值缓存
两个常见治法。布隆过滤器像「黑名单筛」：所有合法 key 先登记，查之前先问它「这 key 可能存在吗」，不存在的直接挡回去，连库都不用碰。空值缓存更简单:库里没有就缓存一个空串（设短 TTL），下次同样的脏 key 直接命中空值返回，不再打库。生产一般俩一起用,双保险。**

## 缓存击穿：一个超热key刚好过期，瞬间全民打库
**击穿和穿透不一样—击穿是「这个 key据库里确实有，而且巨热」，比如首页爆款、顶流博主信息。它突然过期那一刻，成千上个请求同时发现缓存没了，一窝蜂全去查库建缓存，数据库瞬间被这波「集中冲锋」干爆。记住特征：单点、热点、刚好失效。不穿透是查不存在的，击穿是查存在的、但恰巧失效了。**
**怎么治击穿？互斥锁，只放一个线程去重建
互斥锁思路：key 失效时，谁先抢到锁谁去查库重建，其他线程等着，重建完大家再读缓存，数据库只被打一次。进阶还有「逻辑过期」：key 不设真正过期时间，值里塞个过期时间戳，发现逻辑过期就放后台线程异步重建，当前请求先返回旧值，用户无感。锁更稳、逻辑过期更顺，按场景选。**

## 缓存雪崩：一大波 key同时失效，数据库雪崩式崩盘
**雪崩是击穿的「放大版」一不是单个key,而是一批 key 在同一时间集体过期（比如上线时统一设了1小时 TTL，到点全失效），或者 Redis 自己宕机。瞬间海量求穿透到库，数据库直接被打挂，整站瘫疾像雪崩。和击穿的区别：击穿是「一个点」雪崩是「一大片同时」。
怎么治雪崩？错峰过期+高可用兜底
核心是「别让 key 一起死」。给 TTL随机值，比如基础 300 秒 + 随机 0~120秒，让过期时间错开，谁也不撞谁。再加多层兜底：Redis 做主从+ 哨兵（或集群），单机挂了还有备胎；缓存扛不住时给接口加降级，返回默认页。错峰是治本，高可用是兜底,俩都得有。
三兄弟记牢:穿透查无、击穿单热、雪崩成片，治法各自对症。**

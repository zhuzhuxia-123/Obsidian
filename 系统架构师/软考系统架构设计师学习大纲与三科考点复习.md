# 软考系统架构设计师：学习大纲、三科重点与已考考点复习

资料核查日期：**2026年9月29日**。

适用对象：计算机和人工智能基础较薄弱、准备报考软考高级「系统架构设计师」的学生。

## 1. 使用说明与考试概况

### 1.1 先明确考试名称与资料范围

正式资格名称是**系统架构设计师**，通常简称「架构师」或「高架」。本文件针对全国计算机技术与软件专业技术资格（水平）考试，不是其他机构的「系统架构师」认证。

本文件是**自主编排的学习大纲与复习指南**，不是官方大纲全文。以清华大学出版社《系统架构设计师教程（第2版）》和2022年审定的大纲为知识框架，补充近年公开考情中的新技术方向。[教材与大纲版本依据](https://www.tup.tsinghua.edu.cn/bookscenter/book_09190101.html)

阅读时区分三类内容：

- **官方信息**：考试规则、合格标准、教材与大纲版本。
- **已考主题**：公开考后回忆、机构复盘中出现的主题，不等于官方试卷逐字内容；题号、措辞和参考答案可能有差异。
- **建议重点**：结合知识关联与公开考情给出的复习优先级，不代表官方命题概率。

下文「热门」指**值得优先准备**，没有完整、可验证的历年题目数据库，因此不编造出题频率、分值占比或命中率。已考目录是2024—2026上半年的代表性整理，不是全部历史考点清单。2026年下半年尚未举行，不列作已考。

### 1.2 三科分别考什么

| 科目 | 常见形式 | 核心能力 | 备考产出 |
|---|---|---|---|
| 综合知识 | 通常75道单项选择题／75个计分空 | 广泛知识、概念辨析、基础计算 | 知识卡片、专题题集、错题本 |
| 案例分析 | 近年来通常5道大题，第一题必答，其余4题选2题 | 读场景、识别约束、比较方案、写清理由 | 分点答案、架构图、场景分析表 |
| 论文 | 近年来通常4个主题选1个 | 结合项目说明设计、取舍、实施与验证 | 项目素材表、主题提纲、限时全文 |

题型与选答方式以上述近年常见形式说明，最终按当次试卷和机考界面要求执行；近年形式可参考[2025年上半年考生复盘](https://me.51cto.com/p/30913.html?s=i)。

三科通常各满分75分；全国一般合格标准为满分的60%，即45分，各科都须达标，不能用总分抵消某科不足。成绩要求是在同一次考试内通过全部应试科目。[2026年官方报考问答](https://rsj.gz.gov.cn/ywzt/rcgz/rsks/bmtz/content/post_10736860.html)

**机考时间规则：**综合知识与案例分析连考，共240分钟；综合知识最短作答120分钟、最长150分钟，节余时间可用于案例分析。论文单独120分钟。这里采用2026年3月公布的官方规则，当次考务通知、准考证及系统提示优先。[北京市人事考评办公室说明](https://rsj.beijing.gov.cn/ywsite/bjpta/fwzn/cjwt/zyzgks/202603/t20260319_4561593.html)

2026年9月20日下半年批次通告的[公开转载](https://www.hqwx.com/web_news/html/2026-9/17900444721694.html)所列时间规则与上述一致，并提供[职业资格网原文入口](https://www.ruankao.org.cn/article/content/2609211354254868000700041.html)。本次检索未能直接读取该原文页面，因此将转载核对与已直接读取的官方说明分别标注。

模拟建议：先按综合知识135分钟、案例105分钟练习，再根据熟练度调整。案例选题和论文审题均须纳入限时训练。

### 1.3 零基础应该怎样开始

推荐顺序：

**计算机基础 → SQL与网络 → 软件工程与UML → 架构风格 → 质量属性与评估 → 数据库与分布式 → 云原生／大数据／AI → 案例与论文整合。**

可以先学习软件设计师层次的基础内容来补齐知识，但这是一种学习方法，不是必须先取得中级证书。

## 3. 综合知识：热门考点与做题方法

### 3.1 优先掌握的专题

| 专题 | 具体复习点 | 典型提问 | 常见失误 |
|---|---|---|---|
| 架构风格 | 分层、管道过滤器、事件驱动、黑板、解释器、SOA、微服务 | 根据场景选择风格、识别结构 | 只看技术名，不看组织方式 |
| 质量属性 | 性能、可用性、可修改性、安全性、可测试性、易用性 | 判断需求对应的属性 | 看见时间数字就判性能 |
| 架构评估 | SAAM、ATAM、CBAM、效用树、敏感点、权衡点、风险 | 选评估方法、判断设计影响 | 混淆单属性敏感与多属性权衡 |
| 软件工程与需求 | 生命周期、需求分类、原型、敏捷、变更、验证与确认 | 场景选方法、识别阶段成果 | 把用户需求与实现细节混为一谈 |
| UML | 关系、消息、状态转换、活动与部署 | 读图辨义、选择适当图 | 混淆继承、依赖、聚合与组合 |
| 数据库 | 范式、索引、事务隔离、锁、恢复、复制 | 函数依赖、SQL、并发异常 | 将数据库实现差异当作统一规律 |
| 分布式 | 一致性、CAP、事务、幂等、消息、缓存 | 故障与重试下的正确性 | 把CAP简化成随意三选二 |
| 云原生 | 容器、编排、伸缩、探针、发布、可观测性 | 按职责识别组件与机制 | 把容器化等同于完成云原生建设 |
| 安全 | 对称与非对称加密、摘要、签名、认证授权 | 识别安全目的与方案 | 以加密代替鉴权或审计 |
| 基础与计算 | 流水线、Cache、调度、地址、可靠性、路径计算 | 公式与过程计算 | 不写单位、使用公式的前提不成立 |
| 新型存储与AI | 图数据库、向量库、时序库、RAG、端云协同 | 数据与架构选型 | 只记产品名，不懂查询特点 |
| 法规与英语 | 大纲内法律与标准、架构和数据库术语 | 条件辨析、短文理解 | 靠旧题记住已变化的规则 |

综合知识覆盖广。2026年上半年的公开复盘同时提到计算机底层知识与新技术，因此不能只复习AI或云原生。[考后整体分析](https://m.hqwx.com/news/2026-5/17798681439936.html)

### 3.2 概念题复习法

每个概念写一张卡片，包含：

1. 一句话定义。
2. 解决什么问题。
3. 适用场景。
4. 一个代价或限制。
5. 最容易混淆的概念。

例如复习微服务，不止记「拆分服务」，还要能说出业务边界、独立交付、远程调用、分布式数据和运维成本。复习索引，要能解释查询收益与写入、空间成本。

### 3.3 计算题清单

- 流水线执行时间、吞吐率与加速比。
- Cache命中率与平均访问时间。
- 地址空间、页号与页内偏移。
- 调度、同步互斥与死锁场景。
- 网络地址与子网划分。
- 函数依赖、候选键与范式。
- 串并联系统可靠性：只有在给定独立性等前提适用时才使用对应公式。
- 简单路径、资源、成本与概率计算，以实际大纲和题目为准。

建议建立「公式—前提—单位—例题」四栏表，而不是单独背公式。

### 3.4 刷题安排

先做专题题，再做整卷。第一次错题标注原因：概念不会、条件读错、计算错误、术语混淆、资料答案有疑问。第二次复习要求解释每个选项，不只背正确字母。

练习目标可设为完整卷稳定达到55分以上，作为个人训练余量；这不是官方通过线或通过保证。

## 4. 案例分析：热门考点与答题框架

### 4.1 架构风格与质量属性：优先练习

近年公开回忆多次出现质量属性和架构风格组合。第一题常见这一方向，但仍须先读当次题目要求。

质量属性场景需要明确六要素：**刺激源、刺激、环境、制品、响应、响应度量**。[SEI场景定义](https://resources.sei.cmu.edu/asset_files/TechnicalReport/2003_005_001_14213.pdf)

| 属性 | 判断重点 | 原创练习描述 |
|---|---|---|
| 性能 | 延迟、吞吐、资源消耗 | 峰值负载下95%的查询在2秒内返回 |
| 可用性 | 故障后的服务连续与恢复 | 节点宕机后30秒内恢复对外服务 |
| 可修改性 | 修改影响与成本 | 增加一种支付方式仅需修改适配模块 |
| 安全性 | 未授权行为、防护与审计 | 拒绝越权请求并记录审计信息 |
| 可测试性 | 故障定位与测试可执行性 | 可独立替换外部依赖开展回归测试 |

注意：时间数字不必然对应性能；「恢复时间」通常体现可用性，「修改耗时」通常体现可修改性。属性分类以题目定义和候选集合为准。

### 4.2 案例专题训练表

| 专题 | 重点复习 | 推荐练习形式 |
|---|---|---|
| 质量属性与架构评估 | 六要素、效用树、战术、风险与权衡 | 需求分类、场景补全、评价决策 |
| 架构风格 | 结构、构件连接件、数据流、适用条件 | 按题干选择并给出理由 |

| 并发与锁 | 悲观锁、乐观锁、事务、幂等、分布式锁 | 画并发执行时间线 |
| 数据库选型 | 关系、文档、键值、图、时序、向量、搜索 | 数据特征—查询—一致性匹配 |
| 微服务与SOA | 拆分、注册发现、网关、消息、事务、治理 | 补架构图，比较单体与服务化 |

### 4.3 五个必须会解释的易错点

**（1）Redis持久化不等于复制或自动故障转移。** RDB以快照保存数据；AOF记录写操作；复制建立副本。三者服务于相关但不同的目标，不能互相替代。[Redis持久化](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)与[复制文档](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/)

**（2）数据库并发结论要带实现条件。** 脏读、不可重复读、幻读和序列化异常先学通用定义，再看具体数据库；隔离级别名称相同，不代表所有数据库的机制完全一样。[PostgreSQL事务隔离说明](https://www.postgresql.org/docs/current/transaction-iso.html)

**（3）故障检测策略不能直接等同于网络命令。** 考题中的ping/echo可指主动请求—应答式故障检测，不一定只指ICMP工具；心跳也应根据题干说明由谁发送、谁监测以及超时判据。

**（4）部署工具不能替代架构设计。** Kubernetes能够提供容器工作负载管理等能力，但业务边界、数据一致性和权限仍需设计。[Kubernetes概述](https://kubernetes.io/docs/concepts/overview/)

**（5）六边形架构不是规定画六个模块。** 核心是端口与适配器，让业务核心与外部技术交互解耦，便于替换和隔离测试。[Cockburn原始文章](https://alistair.cockburn.us/hexagonal-architecture)

### 4.4 通用答题结构

比较方案题：**需求与约束 → 方案原理 → 优势 → 代价 → 结论与适用条件**。

故障题：**问题现象 → 可能原因 → 改进措施 → 如何验证 → 剩余风险**。

架构图题：**层次职责 → 数据或控制流 → 接口与协议 → 状态在哪里保存 → 失败如何处理**。

答案按要求分点写，每点最好包含「措施＋对应效果」，避免只列产品名称。例如「增加缓存」不如「对可容忍短时陈旧的热点查询增加缓存，降低数据库读取压力，并定义更新与失效策略」。

选题时扫描所有可选题的子问题，按能回答的分值与耗时判断；不要仅因题目写了AI、Redis或云计算就选择。

## 5. 论文：热门主题、素材准备与限时写作

### 5.1 论文与学术论文的区别

软考论文是**围绕指定论题、结合项目进行工程论述**。重点是回答题干子问题，说明设计为什么适合约束、如何实施、怎样验证效果，不是投稿式研究论文，也不要求堆砌参考文献。

字数、摘要与正文分区，以当次题目和机考界面要求为准。练习可以按摘要约250—300字、正文约2000—2500字安排，但这只是训练尺度，不作为所有场次的统一硬性规定。

### 5.2 值得优先准备的主题

| 主题 | 正文要有的技术内容 | 必须交代的取舍 | 建议优先级 |
|---|---|---|---|
| 高并发与性能优化 | 瓶颈定位、缓存、异步、限流、数据库优化、压测 | 性能与一致性、成本、复杂度 | A |
| 高可用与可靠性 | 冗余、故障检测、切换、恢复、演练 | 恢复时间、数据损失窗口、成本 | A |
| 微服务／SOA | 业务边界、接口、治理、事务、演进 | 独立交付收益与分布式复杂度 | A |
| 云原生与自动化运维 | 容器、编排、弹性、可观测性、发布回滚 | 迁移成本与运维能力 | A |
| 事件驱动 | 事件定义、消息流、消费、幂等、补偿 | 解耦与最终一致性、排障难度 | A |
| 数据库与分布式事务 | 数据模型、事务边界、选型与补偿 | 正确性、性能、可用性 | A |
| 大数据架构 | 数据接入、批流处理、存储、服务、治理 | 延迟与准确性、资源开销 | B |
| 测试与质量保障 | 自动化、覆盖、性能、回归、可测试设计 | 覆盖程度与成本、误报漏报 | A |
| 向量数据库与RAG | 数据处理、向量化、索引、召回、权限、评测 | 召回质量、时延、更新成本 | A：近期已考 |
| 六边形架构 | 业务核心、端口、适配器、依赖边界、测试 | 解耦收益与抽象成本 | A：近期已考 |
| AI辅助测试 | 用例生成、执行、判定、人工复核、评估 | 误报漏报、不可重复性与成本 | B：近期已考 |
| 安全架构 | 威胁、身份权限、保护、审计、验证 | 安全与体验、性能、管理成本 | B |

这是准备顺序建议，不是押题名单。某主题已考过，既不能据此判断一定再考，也不能判断不会再考。

### 5.3 零基础的项目素材如何积累

优先整理自己实际参加的课程项目、课题工程、实验室系统或实习项目，明确真实角色与承担内容。没有足够经验时，可以先做教学项目练习设计，不把练习规模描述成未参与过的大型商业项目。

推荐教学项目：**校园文档与图片检索服务**，循序增加用户权限、关系数据库、查询缓存、异步处理、日志指标、向量检索和测试。

这个项目可练习架构设计，但仅完成一个小项目不等于已经具备大型系统经验。后续通过实习或实验室工程补充真实素材。

项目素材表：

| 项目事实 | 要记录什么 |
|---|---|
| 背景 | 服务对象、业务问题、项目边界 |
| 角色 | 自己真正负责的分析、设计、实现或验证工作 |
| 约束 | 时间、资源、性能、安全、兼容性要求 |
| 方案 | 架构图、核心组件、数据流与接口 |
| 取舍 | 候选方案、选择理由、未采用方案的原因 |
| 实施 | 上线或运行步骤、迁移、测试、故障处理 |
| 效果 | 测量方法、负载条件、结果、限制 |
| 改进 | 当前不足、下一步措施 |

### 5.4 可复用的写作结构

1. **摘要**：项目、角色、问题、核心方案与结果。
2. **背景与约束**：解释为什么需要本论题中的设计。
3. **逐项回应题干**：子问题出现的概念与方法必须直接回答。
4. **项目实施细节**：架构、流程、关键决策、异常处理与取舍。
5. **验证与总结**：效果证据、局限、改进。

该结构不是固定评分模板。题干要求的概念、比较、步骤或案例内容必须出现，不能套同一正文应付所有主题。

### 5.5 限时训练

120分钟可分配为：审题选题10分钟、提纲10分钟、输入正文85分钟、检查15分钟。先练一篇完整稿，再练不同主题，建议完成6—8次完整限时训练。

检查重点：题目和子问题是否全部回应；角色是否一致；技术方案是否相互矛盾；指标是否有条件和测量依据；结尾是否解释局限。

## 8. 原创练习与参考答题要点

以下是教学练习，**不是历年真题，也不是官方答案**。

### 8.1 综合题：属性辨析

某系统要求「任一服务节点故障后，30秒内恢复核心查询服务」。主要体现哪一种属性？

A. 性能　B. 可用性　C. 易用性　D. 可修改性

参考：B。关注的是故障后的恢复与服务连续性，不因出现秒数就选择性能。

### 8.2 案例题：六要素

需求：正常业务时段，用户提交查询请求，查询服务应返回结果，95%的请求响应时间不超过2秒。

参考拆解：

| 要素 | 内容 |
|---|---|
| 刺激源 | 用户 |
| 刺激 | 提交查询请求 |
| 环境 | 正常业务时段及题目约定负载 |
| 制品 | 查询服务 |
| 响应 | 处理请求并返回结果 |
| 响应度量 | 95%的请求响应时间不超过2秒 |

真实需求还应明确负载、数据规模与统计窗口，才能复现验证。

### 8.3 案例题：乐观并发控制

多个用户可能同时修改一条记录，系统使用版本号校验。一次更新返回「版本不匹配」，能否直接告知用户成功？

参考：不能。更新未按预期完成，应按业务要求重新读取并重试、提示冲突或交由人工处理。需限定重试次数，避免重复执行有副作用的动作。

### 8.4 案例题：缓存与数据库

商品信息更新后，部分请求仍从缓存读到旧价格。请给出分析框架。

参考要点：检查更新与失效顺序、并发回填、过期时间和消息失败；根据价格业务允许的陈旧窗口设计方案；通过并发测试验证。不要不加条件地宣称某一种删除顺序能够完全解决所有一致性问题。

### 8.5 论文提纲：高并发性能优化

围绕自己参与的服务，说明约束、瓶颈、优化措施与验证。

参考提纲：业务峰值与目标 → 压测和瓶颈定位 → 对比候选方案 → 缓存／异步／查询优化等实际措施 → 正确性与失败处理 → 相同条件下的前后测试 → 限制与改进。

自查：是否只有技术名词？是否说明了数据与负载？是否解释优化引入的代价？是否有未验证的数字？
